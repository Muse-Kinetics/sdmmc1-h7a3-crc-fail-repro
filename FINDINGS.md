# Findings — SDMMC1 `SDMMC_ERROR_DATA_CRC_FAIL` investigation

Full detail behind the summary in [README.md](README.md): what we tried,
what we ruled out, the one result we can't explain, and how to
reproduce each individual diagnostic if you want to dig further
yourself.

## Firmware configuration

- Generated by STM32CubeMX from **STM32Cube FW_H7 V1.13.0**, targeting
  `STM32H7A3ZITxQ` / board `NUCLEO-H7A3ZI-Q`, CMake toolchain output.
  Based on the SDIO/SDMMC 4-bit tutorial at
  https://controllerstech.com/interface-sd-card-with-stm32-via-sdio-4bit-mode/
  (an F446-targeted walkthrough; `Reference/st-sd/SDCARD_SDIO_F446` in
  the parent repo is that original F446 reference project, included for
  comparison) — re-created for the H7A3/SDMMC1 peripheral.
- Real-world/default `SDMMC1` init parameters (`Core/Src/main.c`,
  `MX_SDMMC1_SD_Init()`) — the configuration every result below was
  captured with unless otherwise noted:
  ```c
  hsd1.Init.ClockEdge      = SDMMC_CLOCK_EDGE_RISING;
  hsd1.Init.ClockPowerSave = SDMMC_CLOCK_POWER_SAVE_DISABLE;
  hsd1.Init.BusWide        = SDMMC_BUS_WIDE_4B;
  hsd1.Init.HardwareFlowControl = SDMMC_HARDWARE_FLOW_CONTROL_ENABLE;
  hsd1.Init.ClockDiv       = 0;                   /* ~36MHz bypass */
  ```
  **Updated after ST's reply (ticket 00268848):** `BusWide` is now set to
  `SDMMC_BUS_WIDE_1B` at the first `HAL_SD_Init()` call, switching to
  4-bit afterward via `BSP_SD_Init()`'s own `HAL_SD_ConfigWideBusOperation()`
  call, per ST's suggested fix — see
  [ST-suggested fix](#st-suggested-fix-1-bit-then-switch-buswide-sequencing-tested-no-effect)
  below. Confirmed to produce an identical failure to the direct-4-bit
  init shown above, so every *earlier* result in this document (before
  that section) was captured with the direct-4-bit `BusWide` line as
  written here.
- SDMMC kernel clock: PLL2 @ M=8,N=144,P=2,Q=2,R=4,
  `SdmmcClockSelection = RCC_SDMMCCLKSOURCE_PLL2`, nominal 36 MHz
  feeding `SDMMC1` (see `HAL_SD_MspInit()` in
  `Core/Src/stm32h7xx_hal_msp.c`).
- D-cache/I-cache confirmed **off** (`MPU_Config()` in `main.c` never
  calls `SCB_EnableDCache()`/`EnableICache()`), so cache coherency isn't
  a factor for the IDMA path.
- Everything else (SysTick, USART3 for the ST-LINK VCP, LEDs, user
  button) is CubeMX default; no other peripherals or interrupts are
  active during the test.

## Hardware setup

- **Board:** NUCLEO-H7A3ZI-Q (MB1363-H7A3ZIQ-D01, Rev D), STM32H7A3ZITxQ,
  LQFP144.
- **SD card adapter:** a generic push-pull microSD breakout, male pin
  header plugged directly into the Nucleo's female Zio/Morpho sockets —
  no breadboard, no jumper wires on the 6 SD-bus signals (D0 was also
  tested via a flying jumper on an alternate pin, PC8 — see below).
- **Cards:** two independent cards tested, both fail identically — see
  [Second card](#second-card-samsung-evo) below for why that matters.
  Primary card: 32GB SDHC/SDXC, spec v2.x — CID/CSD below.

**Why D0 is on PB13, not PC8:** CubeMX assigns `SDMMC1_D0` to PB13 by
default in this project, not PC8 — even though PC8 is the pin
physically grouped with the rest of the matched SDMMC bus on the Zio
connector (CN8 pins 2/4/6/8/10/12). PC8 is already committed elsewhere
in this project (originally, card-detect); with PC8 unavailable, PB13
is the *only* other valid `SDMMC1_D0` alternate-function pin on this
chip (confirmed in the H7A3 datasheet's AF table) — CubeMX resolves
this correctly, it isn't a mistake. We also tested D0 relocated to PC8
via a flying jumper (not a clean header-to-header connection like the
other 5 lines) — that configuration was *worse*, not better, most
plausibly because of the jumper's own connection quality rather than
the pin choice itself.

## Card and physical-layer verification

Before concluding anything about the SDMMC1 peripheral/HAL, the card
and the physical bus were both independently exonerated:

- **Card CID/CSD** (read by this project's own `BSP_SD_Init()`, not
  taken on faith — reproduce with `SD_Diag_DumpCardInfo()`, see
  [Diagnostics](#diagnostics-reference) below): ManufacturerID `0x27`,
  OEM/App ID `0x5048`, ProdName `"SD32G"`, Rev `0x60`, SN `0x7396FA05`,
  manufactured Feb 2025. `HAL_SD_GetCardInfo()`: SDHC/SDXC, spec version
  2.x, class `1461`, RCA `0x0001`, 61,071,360 logical blocks × 512B
  (~29.1GiB). Raw CSD: `400E0032 5B590000 E8F77F80 0A400038`.

  the expected `EB 58 90` jump, `"VOLUME   "` volume label, `"FAT32   "`

  `"Non-system disk...Press any key to reboot"` message, and `55 AA` at

### Second card (Samsung EVO)

Swapped in a second, independent microSD card (Samsung EVO) on the same
board/wiring, no other changes, and ran the same repro + diagnostics.

- **Card CID/CSD:** ManufacturerID `0x1B`, OEM/App ID `0x534D`,
  ProdName `"GB1QT"`, Rev `0x30`, SN `0x4B975797`, manufactured Mar
  2019 — a different manufacturer, product, and manufacture date than
  the primary card above. SDHC/SDXC, spec version 2.x, class `1461`,
  RCA `0x0001`, 62,521,344 logical blocks × 512B (~29.8GiB). Raw CSD:
  `400E0032 5B590000 EE7F7F80 0A404054`.
- **`f_mount()` result:** `FR_DISK_ERR` — identical to the primary card.
- **Register-level read of LBA 8192:**
  ```
  STA=0x00000002 DCOUNT=0 dataremaining=0 fifoReads=16
  (DCRCFAIL=1 RXOVERR=0 DTIMEOUT=0 DATAEND=0)
  ```
  Byte-for-byte identical failure signature to the primary card — same
  `DCRCFAIL`-only flag, same `DCOUNT=0`/`fifoReads=16` complete-transfer
  accounting. The corrupted content itself contains recognizable FAT32
  structure (`"SDCARD"` volume label, `"FAT32"` filesystem type visible
  mid-dump), confirming this card also carries a real, valid filesystem
  going in.

**Two cards from different manufacturers, different capacities, and
different manufacture dates fail exactly the same way, with the same
register-level signature.** This directly rules out a single
defective/marginal card as the explanation.

## What we ruled out

Every host-side/software/config lever we could find was tried
independently. All either made no difference or produced a different,
well-understood failure — none fixed the read:

| Variable | Values tried | Result |
|---|---|---|
| Bus width | 1-bit, 4-bit | **Byte-for-byte identical failure.** Rules out anything specific to 4-bit simultaneous-line switching. |
| Clock speed | ~36 MHz down to ~450 kHz (80x range, past the SD spec's own identification-clock ceiling) | **No change.** Rules out signal-settling-time/impedance-margin as the cause. |
| Clock edge | `RISING`, `FALLING` | **No change** (same small set of recurring failure patterns either way). |
| D0 pin | PB13 (matched header), PC8 (flying jumper) | PC8 was *worse* — most plausibly the jumper's connection quality, not the pin choice. Neither fixed it. |
| `HardwareFlowControl` | `ENABLE`, `DISABLE` | `DISABLE` produces a **genuine, different** FIFO-overrun failure (see below) — confirms `ENABLE` is correct/necessary, not a lead on the real bug. |
| Data movement | Polling (`HAL_SD_ReadBlocks`), IDMA (`HAL_SD_ReadBlocks_DMA`) | **Both fail, but not the same way** — see below. Not treated as independent corroboration; the `DATA_CRC_FAIL` finding below is polling-mode only. |
| Read address/content | LBA 8192 (FAT32 VBR), LBA 0 (MBR) | **Same failure signature**, different corrupted content (as expected, since actual content differs). Rules out a fixed-content-dependent bug. |
| DMA/cache coherency | N/A — checked directly | D-cache/I-cache confirmed **off** in this project; not applicable. |
| RX sampling-phase (SDMMC1 delay block, `DLYB_SDMMC1`) | Full sweep: all 12 phase selects × 128 delay units (1536 points) | **0/1536 clean.** Rules out receive-timing skew on the non-matched D0/PB13 net directly, not by inference — see below. |
| SD card | Two, different manufacturers/capacities/mfg dates | **Byte-for-byte identical failure signature on both.** Rules out a single defective/marginal card — see [Second card](#second-card-samsung-evo) above. |

**`HardwareFlowControl=DISABLE` detail:** produces `STA` with
`RXOVERR=1`/`DCRCFAIL=0`, `DCOUNT=480` — only the first 32-byte FIFO
batch was ever drained before the card outran the (disabled) flow
control. This is the textbook overrun signature, and it's useful as a
methodology cross-check: it confirms our instrumentation correctly
detects and reports a real overrun when one genuinely happens, which
increases confidence in the `RXOVERR=0` finding below, where it doesn't.

**IDMA detail:** `HAL_SD_ReadBlocks_DMA()` fails too, including when
run as the very first operation after `Init()` in complete isolation
(ruling out leftover state from other tests) — confirmed twice. But it
fails in a way that doesn't match the polling-mode signature at all:
`hsd1.ErrorCode = RX_OVERRUN | CMD_RSP_TIMEOUT` and zero bytes are ever
written to the destination buffer — no data phase completes at all,
versus polling mode's complete-but-CRC-rejected transfer. A command
*response* timeout on the very first command after a successful
`Init()` is more consistent with an incomplete IDMA setup in this
polling-configured project (H7's SDMMC IDMA needs its own
`IDMABASE`/`IDMACTRL` register setup, which this `.ioc` was not built
around) than with a distinct hardware finding. We're reporting it for
completeness, not relying on it — the `DATA_CRC_FAIL` result above
stands on its own regardless of what's going on with IDMA.

**RX delay-block (`DLYB_SDMMC1`) sweep detail:** the H7A3's SDMMC1 has
a dedicated peripheral (`DLYB_SDMMC1`) for fine-tuning the receive
sampling instant relative to the bus clock — the same mechanism ST's
own HAL uses internally to compensate for trace-length/timing skew when
tuning SDR104/HS200 UHS modes (`SD_HighSpeed()` in
`stm32h7xx_hal_sd.c`). `BSP_SD_Init()`'s normal-speed path never
touches it, so every other result in this document ran with the delay
block unconfigured/bypassed. This was worth testing directly: D0/PB13
is the one non-length-matched net in this bus, and a receive-timing
skew specific to that net would produce exactly the observed signature
(complete transfer, `DCOUNT=0`, no overrun/timeout, `DCRCFAIL=1`). We
swept the full range the silicon supports — all 12 phase selects × 128
delay units, 1536 points, each a real single-block read — and **0/1536
produced a clean read**. Baseline reads immediately before/after the
sweep reproduced the identical `STA=0x00000002 DCOUNT=0 fifoReads=16`
signature, confirming the sweep ran against the same failure, not a
different or already-fixed state. Between this and the PB13 bit-bang
control test above, both the electrical-cleanliness and the
receive-timing-skew explanations for "it's something specific to the
PB13 net" are now directly eliminated, not assumed.

## The critical failure point

This is the one result we can't explain and can't work around from the
host side.

On the real-world configuration (`HardwareFlowControl=ENABLE`,
`ClockDiv=0`, either bus width, either clock edge), a byte-for-byte
re-implementation of `HAL_SD_ReadBlocks()`'s polling loop
(`SD_Diag_RawBlockRead()`, see [Diagnostics](#diagnostics-reference))
prints the raw `STA` and `DCOUNT` registers at the exact moment the
loop exits — *before* the stock HAL's `__HAL_SD_CLEAR_FLAG()` call
wipes the sticky bits (which it does internally, and which would
otherwise hide a simultaneous `RXOVERR` behind the HAL's `if`/`else-if`
`DCRCFAIL`-first error-reporting order):

```
[SD-DIAG] loop exit: STA=0x00000002 DCOUNT=0 dataremaining=0 fifoReads=16
          (DCRCFAIL=1 RXOVERR=0 DTIMEOUT=0 DATAEND=0)
```

- **`DCOUNT=0`** — the peripheral's own hardware data-path counter
  confirms the full, correctly-configured 512-byte length was consumed.
- **`fifoReads=16`** — 16 × 32-byte FIFO batches = exactly 512 bytes,
  matching `DCOUNT` and confirming the software polling loop never fell
  behind the hardware.
- **`RXOVERR=0`, `DTIMEOUT=0`** — no overrun, no timeout.
- **`DCRCFAIL=1`** — the *only* flag set. The hardware's own real-time
  CRC16 check (computed on the bit-serial stream as it's clocked in,
  independent of the FIFO/software drain path) rejected the transfer.

**In short: the hardware's own accounting says it received a complete,
correctly-sized data phase, with no overrun and no timeout, and its own
CRC engine still rejected it.** This isn't a software drain artifact
(disproven directly, not by inference), isn't bus-width- or
clock-speed- or clock-edge-dependent, isn't specific to one block's
content (reproduces on a different LBA with different content), and
isn't specific to one card (two cards, different manufacturers, fail
identically). A verified-good card that reads byte-exact over 1-bit
bit-banged GPIO on this exact board/wiring cannot complete a single
512-byte block read over the real SDMMC1 peripheral, in polling mode,
under any
configuration we could find to try.

## Saleae capture: corruption is on the wire

The open question from the previous version of this document was whether
the bits are already wrong on the wire (pointing at the card/electrical
layer) or whether the wire is clean and the SDMMC1 peripheral's own
receive/CRC datapath is misinterpreting it (pointing at the peripheral
itself). We captured the actual bus (CMD/CLK/D0-D3) during a failing read
and now have a direct answer: **the bits are wrong on the wire.**

Capture, decode script, and full instructions: [`captures/`](captures/).
(`SDMMC1.ClockDiv` was temporarily raised to 40, ~450kHz, for this capture
only — a config already shown above to fail identically to the real-world
`ClockDiv=0`/~36MHz, needed because the 8MHz-class analyzer used here can't
resolve a native 36MHz signal.)

The captured command stream decodes cleanly (validated via CRC7 on every
frame): `CMD0` → `CMD8` → `CMD55`/`ACMD41` → `CMD2` → `CMD3` → `CMD7` →
`CMD17` (`READ_SINGLE_BLOCK`, arg `0x2000` = LBA 8192, our known FAT32-VBR
ground truth). Reconstructing the actual 512-byte block from the four
captured data lanes and diffing it against the known-good ground truth
(`captures/decode_capture.py`) gives a striking, two-part result:

- **Bytes 125–511 (387 bytes — the back three-quarters of the block,
  including the closing `55 AA` boot signature) match the known-good
  content exactly.** 387 consecutive matching bytes is not something that
  happens by chance in an alignment search; the back three-quarters of
  this transfer is genuinely, verifiably clean.
- **Bytes 0–124 (the front quarter — OEM name, BPB, start of the x86 boot
  code) show scattered, clustered corruption** — not uniform noise, but
  small localized dropouts, the same kind of nibble-level shift pattern
  already documented for the *separate* bit-bang 4-bit driver bug in the
  parent repo (`BLOCKER-011`: "nibble-level diffing reveals the true
  single-nibble-drop pattern").

This resolves the open question directly: the wire itself carries bad
bits in part of the transfer, corroborating (not contradicting) the
peripheral's own `DCRCFAIL` verdict — this isn't the peripheral
misreading clean data.

**A further implication worth flagging:** the PB13/D0 net reads
byte-exact via the bit-bang driver, but only ever in **1-bit mode** (D0
only, no other lines switching). The corruption above only shows up in
**4-bit mode** — on both this project's SDMMC1 peripheral *and*,
separately, the parent repo's bit-bang driver's own 4-bit path
(`BLOCKER-011`). That pattern — clean in 1-bit, corrupted in 4-bit, on
two independent driver implementations — is consistent with something
specific to driving all four data lines simultaneously (e.g.
simultaneous-switching noise/crosstalk between the lines, possibly
worsened by PB13's non-matched trace length relative to D1-D3), rather
than two unrelated bugs. We haven't proven this connection, but it's the
most concrete lead either investigation has produced.

## ST-suggested fix: 1-bit-then-switch `BusWide` sequencing (tested, no effect)

ST support (ticket 00268848) pointed to a known CubeMX+FatFs issue and a
specific workaround: call `HAL_SD_Init()` with `hsd1.Init.BusWide` set to
`SDMMC_BUS_WIDE_1B`, then switch to 4-bit afterward via a separate
`HAL_SD_ConfigWideBusOperation(&hsd1, SDMMC_BUS_WIDE_4B)` call, rather
than initializing directly in 4-bit mode.

Worth noting: `BSP_SD_Init()` (`FATFS/Target/bsp_driver_sd.c`, unmodified
CubeMX output) already contains exactly that two-step sequence — but it
was never actually *exercised* as "1-bit then switch" in this repro,
because `hsd1.Init.BusWide` was set to `SDMMC_BUS_WIDE_4B` before the
*first* `HAL_SD_Init()` call, so every call downstream (including the one
inside `BSP_SD_Init()`) was already attempting a direct 4-bit init. This
was a genuinely new code path, not something previously tried.

**Changed `MX_SDMMC1_SD_Init()`'s `hsd1.Init.BusWide` to
`SDMMC_BUS_WIDE_1B`** so the first real `HAL_SD_Init()` call — the one
inside `BSP_SD_Init()`, triggered by `f_mount()` — genuinely initializes
in 1-bit mode first, then switches to 4-bit via `BSP_SD_Init()`'s own
existing `HAL_SD_ConfigWideBusOperation()` call, exactly matching ST's
recommended sequence.

(While in there, also found and fixed a real bug unrelated to ST's
suggestion: `hsd1.Init.HardwareFlowControl` had gone missing from
`MX_SDMMC1_SD_Init()` at some point — silently defaulting to `DISABLE`
`(0x0)` rather than the intended `ENABLE`. Harmless at the `ClockDiv=40`
capture speed used for the Saleae work above, since flow control only
matters once the receiver could plausibly fall behind, but re-added
explicitly before testing ST's fix at full speed to avoid conflating two
different variables.)

**Result: no change.** `f_mount()` still returns `FR_DISK_ERR`, and the
register-level read is byte-for-byte identical to every other
configuration tried:
```
STA=0x00000002 DCOUNT=0 dataremaining=0 fifoReads=16
(DCRCFAIL=1 RXOVERR=0 DTIMEOUT=0 DATAEND=0)
```
This directly rules out the specific CubeMX+FatFs sequencing issue ST
described as the explanation here — that issue's fix changes nothing
about our failure. Left the init order as ST recommended (1-bit then
switch) anyway, since it's the more defensive/correct pattern regardless
of whether it's the fix.

## Recommended next step

Every host-side/software/config lever we could find has been tried
(width, speed, edge, flow control, pin, data-movement mechanism, address,
RX sampling phase, and now ST's own suggested init-sequencing fix), and
the actual bus signals have been captured and show real, physical
bit-level corruption concentrated in part of the transfer. We believe the
next productive step is on the electrical side: checking for
simultaneous-switching noise/crosstalk between the four data lines during
a real 4-bit transfer (e.g. an oscilloscope capture of the analog
waveforms, not just digital logic levels, focused on the corrupted region
of the transfer), and/or advice from ST on whether this board's
trace-length mismatch on D0 (PB13 vs. the matched CN8 group) is expected
to cause this class of failure in 4-bit mode specifically.
